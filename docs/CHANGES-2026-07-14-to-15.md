# API Changes — 2026‑07‑14 → 2026‑07‑15

> For the engineer building the backoffice. This is **what changed, how it works now, and how to
> build against it** — not the rationale. Each entry links to the commit. Two of these are
> **breaking** for anything that already consumed the read endpoints; the rest are additive.
>
> Companion doc: `BACKOFFICE-IMPLEMENTATION-GUIDE.md` (full current behavior).

## TL;DR

| # | Change | Kind | Where it hits you |

## 1. Reads are open — participant access machinery removed  *(breaking)*
Commits `903de45` (ADR), `4285c6f` (phase 2), `dae860a` (phase 3)

**What changed.** The whole "who may see this escrow" layer was deleted. Escrow state is public
on‑chain, so the read‑model treats it as public too. The **access‑grant endpoints and DTOs were
removed** (e.g. the old `escrow-access-grant` routes/`grant` DTOs no longer exist). GraphQL args and
read DTOs tied to participant‑gating were dropped.

**How it works now.**
- Any authenticated caller with `ESCROW_MANAGER` can read **any** escrow on the network via
  `GET /escrows/**` and GraphQL.
- Caller identity matters in exactly one place on reads: the listing's `scope` param. `scope=mine`
  (default) returns escrows that *concern* the caller (verified‑wallet participation ∪ platform
  attribution); `scope=all` returns everything on the network. This is **segmentation, not access
  control**.
- Tenant filters `platformId` / `subjectId` are still gated: the caller must own that platform,
  else `403 ESCROW_FILTER_FORBIDDEN`.

**How to build.** Do not implement per‑escrow "can view" checks. Use `scope=mine` to show "my
escrows", `scope=all` for an operator/global view, and `platformId`/`subjectId` to segment your own
tenants. Remove any calls to the old access‑grant endpoints — they're gone.

## 2. Amounts in human token units across all reads  *(breaking)*
Commit `37c36c9` (reads) + `59b67ad` (transaction build side)

**What changed.** Read‑model money fields are no longer raw on‑chain base‑unit integers. They are
**human token units as decimal strings**.

**How it works now.**
- `balance`, `totalAmount`, `totalDeposited`, `totalReleased`, `pendingRelease`,
  `nextRelease.amount`, deposit `amount`, and the amounts inside `snapshot`/`milestones` are decimal
  strings like `"250.5"`.
- `platformFee` is a percent decimal string (`"5"` = 5%).
- On the **build side**, request `amount`s remain human numbers (e.g. `250.5`); the service scales
  them to base units using the trustline token's decimals before building the XDR.

**How to build.** Parse read amounts as decimals/strings, not integers — **do not divide by 1e7
yourself anymore**; the API already did the scaling. Keep sending human numbers in build bodies.
Use a decimal‑safe representation if you do math (values are strings precisely to avoid float loss).

## 3. Per‑token decimals via `stellar_asset` metadata cache
Commit `298afc7`

**What changed.** Scaling is per‑token, not hard‑coded to 7. The Indexer resolves each token's
SEP‑41 `decimals()` once and caches it (`stellar_asset` table); the read edge scales each amount by
that token's real decimals.

**How it works now.** USDC and other classic SACs are 7; a custom SEP‑41 token can be anything in
`[0, 18]`. Unknown/unresolved tokens fall back to 7. This all happens server‑side at read time (no
chain call on the hot path).

**How to build.** Nothing special — just trust the decimal strings you receive. If you display the
token, use the new `asset` object (below) rather than assuming "7 decimals / USDC".

## 4. Escrow root `asset` object  *(additive)*
Commit `cdcbf70`

**What changed.** Every escrow read now carries a structured trustline asset at the root.

**Shape:**
```json
"asset": {
  "name": "USDC",
  "address": "GBBD47IF6LWK7P7MDEVSCWR7DPUWV3NY3DTQEVFL4NAT4AQH3ZLLFLA5",
  "contractId": "CBIELTK6YBZJU5UP2WWQEUCYKLPU6AUNZ2BQ4WWFEIE3USCIHMXQDAMA"
}
```
- `name` = asset code / SEP‑41 symbol (e.g. `USDC`); `null` while unresolved.
- `address` = issuer account (G…) of a wrapped classic asset; `null` for pure Soroban tokens.
- `contractId` = the Soroban token contract (C…) from the escrow's trustline.
- The whole object is `null` until the first state is projected. Present on both REST
  (`EscrowSummary.asset`) and GraphQL (`Escrow.asset { name address contractId }`).

**How to build.** Render the asset from this object. Note the older `EscrowFinancial.asset` field is
still a plain string (`"USDC:G..."`); the structured object lives at the escrow root/summary.

## 5. `balance` on all main reads  *(additive)*
Commit `1831fff`

**What changed.** `balance` now appears on the escrow **list**, **detail**, **batch details**, and
the **GraphQL root** `Escrow` type — previously it only existed on `GET /escrows/financial`.

**How it works now.**
- `balance` = **projected** balance = `totalDeposited − totalReleased`, in human units, **always
  present** (`"0"` when nothing is deposited). Same number as `financial.balance` — one shared
  derivation, so REST/GraphQL/financial can't disagree.
- It is fed by the Indexer's **deposit trail**: each deposit event the Indexer records into
  `escrow_deposit` raises `totalDeposited`, so the next read reflects it. It is **eventually
  consistent** with the on‑chain token balance — the authoritative live balance is
  `GET /escrow-balances` (reads the chain directly).

**How to build.** Show `balance` straight from the list/detail read — no extra `/financial` call for
a headline number. For a guaranteed‑live figure (e.g. a settlement screen) use the on‑chain
`GET /escrow-balances`. After a fund/release, expect `balance` to update once the Indexer catches
up.

## 6. `createdByUserId` / `creatorAddress` removed from reads  *(breaking)*
Commit `f064583`

**What changed.** Off‑chain authorship is **no longer exposed on any read**. These two fields
previously appeared on `GET /escrows/:contractId` and `GET /escrows/details`; they are now gone from
every read payload (REST and GraphQL). The `EscrowStateResponse` type collapsed into
`EscrowSummaryResponse`.

**How it works now.** The data is still recorded internally (deploy‑time stamping + DB columns) but
never leaves on a query. Reads expose only on‑chain / public information plus the projected
balance/asset.

**How to build.** Remove any UI that showed "created by user / creator address" from escrow reads.
If you need the deploy signer, it is on‑chain (reconstructable from the transaction), not from these
endpoints.

---

## 7. Zero `receiverMemo` omitted from deploy response  *(additive)*
Commit `910691a`

**What changed.** When you deploy and then `POST /stellar/send-transaction`, the returned `escrow`
snapshot **omits `receiverMemo` when it is `0`**. On **v2** it is always omitted; on **v1** it is
omitted only when `0` (non‑zero v1 memos are still returned).

**How to build.** Treat a missing `receiverMemo` as "not set / 0". Don't rely on it being present in
deploy responses.

---

## 8. Throttling budgeted per credential  *(behavioral)*
Commit `e41a246`

**What changed.** Rate‑limit buckets are keyed **per credential** — per api‑key id, per session
token, or per IP for public routes — instead of a single per‑IP budget.

**How it works now.** Each api‑key/session gets its own budget; one noisy tenant no longer eats
another's quota. Exceeding it → `429 TOO_MANY_REQUESTS` (Problem Details). `POST
/auth/bootstrap-admin` is separately tightened.

**How to build.** Handle `429` with backoff. If the backoffice fans out many reads (e.g. dashboard
refresh), prefer batch endpoints (`/escrows/details|financial|milestones`, up to 50 ids) and
GraphQL field‑selection to stay under budget, and paginate with cursors rather than hammering.

## Migration checklist for the backoffice

- [ ] Parse read amounts as **decimal strings** (drop any client‑side base‑unit division).
- [ ] Render the token from the new **`asset { name, address, contractId }`** object.
- [ ] Use **`balance`** directly from list/detail; reserve `/escrow-balances` for live figures.
- [ ] Delete any usage of **access‑grant** endpoints and of **`createdByUserId`/`creatorAddress`**.
- [ ] Drive visibility with **`scope=mine|all`** + tenant filters, not per‑escrow access checks.
- [ ] Handle **`429`** (per‑credential) and **`STELLAR_TX_SUBMITTED_INDEXER_LAGGING`** (eventual
      consistency).
- [ ] Treat missing **`receiverMemo`** as 0.
